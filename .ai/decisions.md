# Лог решений (ADR-лайт)

## Решение: Система истории для ИИ-агентов
**Дата:** 2026-10-11 | **Статус:** принято

**Контекст:** проект будет развиваться с помощью ИИ-агентов, нужна непрерывность контекста между сессиями.

**Варианты:** A) только git-история; B) отдельная директория `.ai/` с журналом, контекстом и логом решений.

**Решение:** B.

**Почему:** git-история не объясняет «почему» и не даёт быстрого входа в контекст; `.ai/` даёт агентам явную точку входа (`AGENTS.md` → `context.md` → `journal.md`).

## Решение: Контент генерирует ИИ-агент, roadmap.sh — как скелет
**Дата:** 2026-10-11 | **Статус:** принято

**Контекст:** пользователь хочет, чтобы обучающий контент не писался вручную, а самостоятельно искался/генерировался ИИ-агентом.

**Варианты:**
- A) Ручной контент (статические уроки в JSON/MD).
- B) Полностью генеративный агент: LLM генерирует уроки на лету по запросу.
- C) Гибрид: roadmap.sh задаёт структуру тем (скелет), ИИ-агент генерирует уроки заранее (пайплайн) и кладёт в базу; бот только выдаёт готовое.

**Решение:** C (гибрид).

**Почему:** генерация на лету (B) — медленно, дорого и нестабильно по качеству; ручной (A) — не масштабируется. Гибрид даёт воспроизводимые уроки, кэширование, возможность ревью перед отправкой и офлайн-работу бота.

**Следствия:** нужен отдельный модуль контент-агента (генерация уроков по теме из roadmap), хранилище уроков (SQLite), API-ключ LLM в `.env`.

## Решение: LLM-провайдер — OpenRouter
**Дата:** 2026-10-11 | **Статус:** принято

**Контекст:** контент-агенту нужен LLM-провайдер для генерации уроков.

**Варианты:** A) прямой API одной модели (OpenAI/Anthropic/…); B) OpenRouter; C) локальная модель.

**Решение:** B (OpenRouter).

**Почему:** один API-ключ даёт доступ ко всем major-моделям — можно менять модель генерации без кода и подбирать дешёвые для конвейерной генерации. Модель фиксируется в `meta.model` урока, так что перегенерация воспроизводима.

**Следствия:** ключ `OPENROUTER_API_KEY` в `.env`; контент-агент ходит в `https://openrouter.ai/api/v1` (OpenAI-совместимый API); выбор модели — через конфиг/`.env`, не хардкодом.

## Решение: Схема урока v1
**Дата:** 2026-10-11 | **Статус:** принято

**Контекст:** нужен единый формат урока между контент-агентом (генерация) и ботом (выдача в Telegram).

**Решение:** JSON-документ, описанный `docs/lesson.schema.json` (JSON Schema draft 2020-12), дизайн — `docs/lesson-schema.md`, эталон — `docs/examples/lesson-what-is-the-internet.json`.

**Ключевые свойства схемы:**
- Урок = данные: жёсткие лимиты полей, чтобы любой блок влезал в сообщение Telegram (4096); каждая секция `theory` = одно сообщение.
- Квиз машино-проверяемый: `correct` — 0-based индексы вариантов; `single` → ровно 1, `multi` → 1+. Правило kind/correct проверяет валидатор пайплайна (JSON Schema этого не выразит).
- Геймификация встроена: `xp` за урок, `key_terms` → будущие карточки повторения.
- Жизненный цикл: `draft → review → published → archived`; бот отдаёт только `published`.
- `meta.model` + `prompt_version` фиксируют, чем и как урок сгенерирован (воспроизводимость).
- В SQLite тело урока — колонка `json`; поля выборки (roadmap_id, order, status, difficulty, language, xp) денормализованы в колонки.

**Следствия:** валидатор (`validate_lesson`) = JSON Schema + семантика квиза + лимиты рендера; пример урока — fixtures для тестов валидатора.
